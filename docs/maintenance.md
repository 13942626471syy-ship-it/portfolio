# 维护说明

## 公开资料结构

每个项目保留一份简短介绍，包含目标、功能范围、技术结构、当前状态和维护摘要。详细实现、原始问题记录及验收证据继续保存在各项目的私有维护空间。

## 记录原则

- 只记录已经完成或能够核实的变更，不补写虚构提交历史。
- 区分历史验证、当前验证和计划工作。
- 明确测试的版本与范围，不把局部通过写成全量通过。
- 截图、视频和示例数据在发布前单独审核。
- 公开介绍发生变化时，在本仓库的更新记录中说明。

## 私有项目建议保留的维护入口

- 启动与配置说明，以及不含真实值的环境配置示例。
- 架构说明、接口与数据契约。
- 测试入口、验收范围与已知问题。
- 版本更新、发布说明与恢复办法。
- 第三方依赖、素材来源与许可记录。

以上是维护结构说明，不表示所有项目的这些入口已经补齐。

## 自动检查

需要 Python 3.10+ 与 Git，无第三方 Python 依赖。在本展示仓库根目录运行：

```bash
python -m unittest discover -s tests -v
python scripts/validate_showcase.py
```

[CI 配置模板](ci.md)可用于 push、pull request 或手动触发，云端工作流目前尚未启用。模板仅授予 `contents: read`，不读取 Secrets、不运行私有产品；官方 checkout action 固定到提交版本。

检查内容：

- Markdown / HTML 中的本地目标、中文标题锚点和图片路径。
- 12 张已审核 PNG 的 SHA-256、尺寸、嵌入文本与 EXIF 元数据；素材新增或变化需要更新审核清单。
- Git 已跟踪与未忽略文件是否落在公开展示白名单，阻止误加源码目录、数据库、日志、压缩包或视频。
- 常见凭据格式；检查报告不回显匹配值。

脚本不请求外部网址，外链可用性需在发布时单独检查。它也不能理解图片里的个人信息或判断项目成果是否真实；人工素材审核与源码核对仍是必要步骤。

## 更新顺序

1. 在独立展示副本修改文档，先核对目标工程和版本，再写技术与成果。
2. 新素材逐张审查，保留原始界面与示例性质说明，随后更新 `assets/manifest.json`。
3. 执行自动检查并查看差异，确认只包含公开资料。
4. 发布后查看 GitHub 实际渲染，检查入口、图片和架构图；CI 启用后还需检查 Actions 结果。将实际范围记入[核验记录](verification.md)。
